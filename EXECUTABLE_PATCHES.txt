T3-ModTools executable patches
==============================

T3-ModTools 0.6.5 stores the compiled archive at <game>/modtools_data/Mods.Cod and
build/loader reports at <game>/modtools_data/.compiled/. T3_Modded.exe and optional
A2.Dll remain in the game folder. The corrected loader places its code and package path
in a dedicated appended .t3ldr section with read/execute permissions. Original sections
remain unchanged except for the six-byte loader hook and selected mod patches; PE headers
are updated to describe the new section.

Migration verifies recognized older loader bytes and manifest fingerprints, restores the
original storage occupied by that loader, and installs the dedicated-section loader while
preserving the existing mod patches. Previous generated files are backed up under
modtools_data/legacy_backup/. Launch requires the corrected loader; if migration cannot
verify an older executable, retain the old archive and run Build Mods + Modded EXE with
the intended mods enabled before launching.

The initial 0.6.5 implementation enlarged a loader string in the original .data section.
The added bytes overwrote a live empty-string sentinel used by menu lookup, causing a
crash. Zero-filled original bytes are not sufficient evidence that storage is unused.
The correction keeps version 0.6.5 and allocates all loader storage in .t3ldr instead.

Optional per-mod path:

  <mod>/patches/executable.json

For flat mod folders, <mod>/executable.json is also accepted as a fallback.

Optional generated-manifest convention:

  <mod>/runtime_patch.py

When Build Mods + Modded EXE starts, enabled root-level runtime_patch.py generators are
synchronized with --write using the same Python interpreter as T3-ModTools. A reviewed
generator may declare runtime_cache in mod.json (see README.txt) to reuse a successful
result when all declared inputs and generated files still match their SHA-256 fingerprints.
Undeclared generators always execute. The resulting executable.json
is parsed before previous build outputs are staged. A nonzero exit, invalid manifest, missing
manifest, or 60-second timeout aborts the build without replacing the last valid Mods.Cod,
T3_Modded.exe, and A2.Dll set. Disabled project generators are never executed. These scripts are executable
local code; only enable generators from trusted projects.

Version 1 schema:

{
  "format_version": 1,
  "target": "T3.exe",
  "patches": [
    {
      "id": "my_patch",
      "description": "What this patch changes",
      "type": "aob_replace",
      "section": ".text",
      "pattern": "AA BB ?? DD",
      "replacement": "11 22 ?? 44",
      "expected_matches": 1
    }
  ]
}

For code or data injection away from a unique anchor, use aob_write:

{
  "id": "my_injection",
  "description": "Write validated bytes relative to a unique signature",
  "type": "aob_write",
  "section": ".text",
  "pattern": "AA BB CC DD",
  "write_offset": "0x20",
  "expected_fill": "00",
  "replacement": "11 22 33 44",
  "expected_matches": 1
}

Rules:
- The manifest-level target defaults to T3.exe. An individual patch may override it with
  "target": "Ai.Dll".
- Patterns are searched against the corresponding original T3.exe or Ai.Dll, never a
  previously modded binary.
- ?? in pattern matches any byte.
- ?? in replacement preserves the original byte.
- For aob_replace, pattern and replacement must have the same length.
- For aob_write, write_offset is relative to the unique pattern match; expected and
  replacement must have the same length, and the destination must remain in section.
- expected_fill may replace expected when every original destination byte must have the
  same value; it expands to the replacement length.
- aob_write validates expected against the corresponding original binary before writing.
- Version 1 requires expected_matches = 1.
- Section may be .text, .rdata, .data, .tls, .data1, .rsrc, or all.
- Conflicting writes from enabled mods stop the build. Identical writes may coexist.
- Build Mods + Modded EXE recreates Mods.Cod, T3_Modded.exe, and A2.Dll when required.
- T3.exe and Ai.Dll are never overwritten; Ai.Dll patches are written to A2.Dll.

Owned code extensions (loader_extension)
---------------------------------------

A mod may place additional code and read-only constants in the newly appended
.t3ldr section. This avoids treating zero-filled original game storage as free
space. It does not install a hook by itself: use separately guarded aob_replace
or aob_write entries for the original call sites that should reach the extension.

Version 1 also accepts this patch entry:

{
  "id": "my_owned_code",
  "description": "Code and read-only constants in the generated loader section",
  "type": "loader_extension",
  "target": "T3.exe",
  "expected_original_sha256": "52f68d5df4912aba662f0371a06ae0b1ec447ef4b7338460224b20904eb0f061",
  "virtual_address": "0x11C0000",
  "replacement": "90 C3"
}

The address is an example, not a shared allocation to reuse in every mod. A
generator must select a nonoverlapping address for the supported original image
and compile any absolute operands and relative branches for that exact address.
There is no implicit relocation or automatic reassignment of requested addresses.

Extension-specific rules:
- Only T3.exe is supported; Ai.Dll extensions are rejected. The supported image
  is fixed-base PE32. ASLR and relocatable images remain unsupported.
- expected_original_sha256 is required and must exactly equal the lowercase
  SHA-256 of the pristine T3.exe used by this build.
- virtual_address is an absolute virtual address, not an RVA or file offset. A
  decimal integer or a decimal/0x-prefixed integer string is accepted.
- replacement contains concrete hexadecimal bytes only: no ?? wildcards. Each
  entry must contain 1 through 65,536 bytes.
- section, pattern, write_offset, expected, expected_fill, and expected_matches
  belong to AOB patches and are not used by loader_extension.
- All enabled extensions are ordered by address. Their intervals must not
  overlap, including identical overlapping bytes from separate mods. Adjacent
  intervals are accepted. This is stricter than identical ordinary AOB writes.
- Automatic ANM and material support code occupies the beginning of the loader
  extension area. A requested address must follow that generated code and all
  earlier requested extensions. A gap may be at most 65,536 bytes; unused gaps
  are filled with INT3 bytes (CC). The combined extension area, including
  automatic code and gaps, may not exceed 1 MiB.
- The destination must be owned new loader storage. Original sections, loader
  trampoline bytes, and loader strings cannot be destinations. .t3ldr is read/
  execute and is not writable; do not place mutable runtime state in this area.
- Hash, size, range, overlap, and original-hook conflicts are checked before any
  generated executable or DLL is written. Invalid entries leave the preceding
  compiled outputs in place. The originals T3.exe and Ai.Dll are never changed.
- The loader manifest records the actual file offset and size for each extension.
  Rebuilds always derive a fresh .t3ldr section from the original executable.
